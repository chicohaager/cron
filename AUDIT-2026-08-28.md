## 🔴 1. Der Scheduler ignoriert beide Tagesfelder

**Fundstelle:** `cmd/cron/main.go:1463`

```go
dayOk := (domSet.isAll && dowSet.isAll) || (domSet.isAll && dowOk) || (dowSet.isAll && domOk) || (domOk || dowOk)
```

Der letzte Term `(domOk || dowOk)` ist mit ODER angehängt und schluckt damit die drei
davorstehenden Fälle. Ist eines der beiden Tagesfelder `*`, ist dessen Menge vollständig
gefüllt, sein `…Ok` also immer `true` — und damit `dayOk` immer `true`.

**Beleg** (gegen die laufende API, Messtag war Freitag, 2026-08-28):

```
POST /cron/tasks  {"type":"cron","cron_expr":"<expr>"}  →  next_run_at auslesen

0 2 * * 1   (Montag 02:00)    ->  Samstag 2026-08-29 02:00   erwartet: Montag 2026-08-31
0 5 1 * *   (1. des Monats)   ->  Samstag 2026-08-29 05:00   erwartet: 2026-09-01
0 2 * * *   (täglich 02:00)   ->  Samstag 2026-08-29 02:00   korrekt
```

**Wirkung:** Jeder wochentags- oder monatstagsgebundene Task läuft **täglich**. Ein
wöchentliches Backup läuft 7×, ein monatliches ~30× so oft. Betrifft auch die Vorschau
`next_runs` in `POST /cron/cron/validate`, die dieselbe Funktion benutzt.

**Vorschlag:** Die Vereinigungsregel von POSIX-cron ausschreiben — ODER nur, wenn *beide*
Felder eingeschränkt sind, sonst UND:

```go
switch {
case domSet.isAll && dowSet.isAll:
    dayOk = true
case domSet.isAll:      // nur Wochentag eingeschränkt
    dayOk = dowOk
case dowSet.isAll:      // nur Monatstag eingeschränkt
    dayOk = domOk
default:                // beide eingeschränkt -> ODER (POSIX)
    dayOk = domOk || dowOk
}
```

**Achtung bei `*/n`:** `parseCronField` setzt `isAll = true` auch für `*/15`
(`cmd/cron/main.go` im `*/`-Zweig). Für die Tagesfelder ist das falsch — `*/2` im
Monatstagsfeld ist eine *Einschränkung*, kein `*`. Beim Fix mit reparieren, sonst ist
`0 2 */2 * *` weiterhin täglich.

## 🔴 2. Monatsnamen und Wochentagsbereiche validieren, laufen aber nie

**Fundstellen:** `internal/cron/validate.go:105` und `:170` (akzeptieren `jan`…`dec`)
gegen `cmd/cron/main.go:1478` `parseCronField` (kennt Aliase **nur** für den Wochentag,
und dort nur als Einzelwert, nicht im Bereich).

**Beleg** (direkter Aufruf von `cronNext` aus einem Wegwerf-Test):

```
0 0 1 jan *      ->  NIE (Nullzeit)          Validator: gültig
0 2 * * mon-fri  ->  Log "Invalid cron range \"mon-fri\", skipping",
                     danach täglich (Befund 1)
30 3 * * mon     ->  Alias erkannt, aber täglich (Befund 1)
```

**Wirkung:** Ein Task mit `jan` wird angelegt, zeigt `next_run_at: 0` und feuert nie —
ohne Fehlermeldung im UI. Der Validator sagt „gültig", der Scheduler kann es nicht.

**Vorschlag:** Aliastabellen zusammenlegen. `internal/cron` bekommt die einzige
Namensauflösung (`weekdayAlias`, `monthAlias` sind dort schon vorhanden), `parseCronField`
ruft sie auf — für Einzelwerte **und** für beide Seiten eines Bereichs. Danach ist
„Validator sagt gültig" gleichbedeutend mit „Scheduler kann es". Am besten mit einem Test,
der genau diese Äquivalenz prüft: für jeden Ausdruck einer Liste muss
`Validate(e).ok == (cronNext(e, t0) != Nullzeit)` gelten.

## 🔴 3. Data Race mit Nil-Panic im Intervall-Scheduler

**Fundstellen:** `cmd/cron/main.go:571` (`case <-t.ticker.C:` im Goroutine-`select`)
gegen `cmd/cron/main.go:595` (`t.ticker = nil` in `clearSchedule`).

Das `select` wertet `t.ticker.C` bei **jedem** Schleifendurchlauf aus, ohne Lock.
`clearSchedule` schließt `done` und setzt `t.ticker` unmittelbar danach auf `nil`.
Zwischen beiden liegt ein Fenster.

**Beleg** (Wegwerf-Test: Intervall-Task mit 2 ms starten, 50× im Millisekundentakt
pausieren/fortsetzen, unter `go test -race`):

```
2 × WARNING: DATA RACE
    Write at … clearSchedule()   main.go:595
    Read  at … startSchedule.func1()  main.go:571
panic: runtime error: invalid memory address or nil pointer dereference
```

**Wirkung:** `t.ticker.C` auf einem `nil`-Ticker ist ein echter Nil-Dereferenz — kein
Artefakt des Race-Detektors. Der Panic reißt den **gesamten Dienst** mit, also alle Tasks.
`Restart=always` in der Unit fängt es auf, die laufenden Ausführungen sind weg. Auslöser im
Alltag: Pause, Resume oder Löschen kurz vor einem Tick. Bei Intervallen in Minuten ist das
Fenster schmal — aber es ist ein Rennen, also in Tests unsichtbar und im Betrieb sporadisch.

**Vorschlag:** Den Kanal **einmal** vor der Schleife festhalten und `done` als einziges
Abbruchsignal benutzen:

```go
ticker := time.NewTicker(t.Interval)
done := make(chan struct{})
t.ticker, t.done = ticker, done
go func(id string, c <-chan time.Time, done <-chan struct{}) {
    defer ticker.Stop()
    for {
        select {
        case <-done:
            return
        case <-c:
            …
        }
    }
}(t.ID, ticker.C, done)
```

Gleiche Familie, gleiche Stelle mitnehmen: `scheduleCronNext` liest `t.Status` und schreibt
`t.NextRunAt`/`t.timer` in der `AfterFunc`-Rückrufe ohne Lock; die Ticker-Goroutine schreibt
`tt.NextRunAt` ohne Lock (`main.go` im `case <-t.ticker.C`-Zweig).

**Dauerhafter Schutz:** `go test -race ./...` in die CI, und ein Test, der Pause/Resume
gegen einen laufenden Ticker fährt (der obige Wegwerf-Test taugt als Vorlage).

## 🔴 4. Unauthentifizierte Codeausführung als root aus dem LAN

**Fundstellen:**
- Keine Auth im Backend — Grep über `cmd/` und `internal/` findet weder JWT-Prüfung noch
  Auth-Middleware; alle 14 Routen (`cmd/cron/main.go:207–220`) antworten ohne jeden Header.
- `raw/usr/lib/systemd/system/cron.service` hat **kein** `User=` → System-Unit läuft als root.
- Kommandos laufen über `exec.CommandContext(ctx, "/bin/sh", "-lc", taskCommand)`
  (`cmd/cron/main.go:667`), also als root.
- `withCORS` (`cmd/cron/main.go:259`) spiegelt in Zeile 263 **jede** `Origin` zurück und
  beantwortet den Preflight mit `Allow-Headers: Content-Type`.

**Gemessen in dieser Sitzung:** Jeder Endpunkt antwortet ohne Anmeldung (alle Messungen
oben liefen mit blankem `curl`, ohne Header, ohne Cookie).

**Aus einer älteren Messung übernommen (2026-05-20, ZimaOS v1.6.1, nicht in dieser
Sitzung nachgeprüft):** Das ZimaOS-Gateway erzwingt **keine** Authentifizierung; es proxied
registrierte Routen verbatim. IceWhale-eigene Dienste prüfen den JWT selbst, Community-Module
tun das in der Regel nicht. Konsequenz: die Route `/cron` hängt über Port 80 im LAN.
**Vor dem Fix einmal auf dem Zielhost gegenprüfen**, ob das für die eingesetzte
ZimaOS-Version noch gilt — die Aussage ist drei Monate alt.

**Wirkung:** Zwei getrennte Wege, beide mit Root-Ergebnis:
1. Jedes Gerät im LAN kann per `POST /cron/tasks` einen Task mit beliebigem Kommando anlegen
   und per `POST /cron/tasks/{id}/run` sofort ausführen lassen.
2. Weil `Origin` gespiegelt wird und der Preflight `Content-Type` erlaubt, genügt es, dass
   jemand im LAN im Browser eine beliebige Webseite öffnet — deren JavaScript kann denselben
   Aufruf machen. Es sind keine Anmeldedaten nötig, also scheitert es auch nicht daran, dass
   der Browser keine Cookies mitschickt.

**Vorschlag:**
- Auth-Middleware vor alle Routen außer `/cron/health`: ES256-Signatur des ZimaOS-JWT gegen
  die JWKS des user-service prüfen (Go-Standardbibliothek reicht: `crypto/ecdsa` +
  P-256; Signatur ist `r‖s`, je 32 Byte), dazu `exp` prüfen und den `iss`-Claim **als Menge**
  pinnen. Access- und Refresh-Token sind mit demselben Schlüssel signiert — wer nur Signatur
  und `exp` prüft, akzeptiert den langlebigen Refresh-Token als Session. Der Issuer-Name hat
  sich zwischen ZimaOS-Versionen geändert; eine Liste statt eines festen Strings verhindert,
  dass ein OS-Update das Modul komplett aussperrt. JWKS-Port **nicht** hartkodieren, sondern
  über die Gateway-Routentabelle auflösen.
- Frontend: die ZimaOS-Shell hängt das Token nicht automatisch an Modul-Fetches an. `app.js`
  muss `Authorization: 'Bearer ' + localStorage.getItem('access_token')` selbst setzen.
- CORS gleichzeitig verengen: keine Spiegelung, sondern die eigene Origin.
- Zusätzlich erwägen: Kommandos nicht als root ausführen (`User=` in der Unit, oder ein
  konfigurierbarer Ausführungsbenutzer je Task). Das begrenzt den Schaden auch dann, wenn
  die Auth einmal umgangen wird.

## 🟠 5. Export und Import passen nicht zusammen — Tasks verschwinden stumm

**Fundstellen:** `exportHandler` (`cmd/cron/main.go:1110`) serialisiert `Task`, dessen
Intervallfeld `interval_ms` heißt (`cmd/cron/main.go:35`). `importHandler`
(`cmd/cron/main.go:1130`) dekodiert nach `createReq`, das `interval_min` erwartet
(`cmd/cron/main.go:305`), und überspringt bei `req.IntervalMin < 1` per `continue`
(`cmd/cron/main.go:1166`).

**Beleg:** 4 Tasks (3× cron, 1× interval) exportiert, derselbe Export wieder importiert:

```
GET  /cron/export   ->  4 Tasks in der Datei
POST /cron/import   ->  {"imported":3}
```

Der Intervall-Task fehlt. Keine Fehlermeldung, kein Warnhinweis, kein Statuscode ≠ 200.

**Wirkung:** Wer sein eigenes Backup zurückspielt, verliert alle Intervall-Tasks und merkt
es nicht. Das ist die gefährlichste Form: der Nutzer glaubt, ein Backup zu haben.

**Vorschlag:** Ein gemeinsames Austauschformat für beide Richtungen (eigener `exportTask`-Typ
mit `interval_min`), plus eine Antwort, die Übersprungenes **benennt**:
`{"imported":3,"skipped":[{"name":"…","reason":"interval_min fehlt"}]}` — und im UI anzeigen.
Ein `continue` ohne Rückmeldung ist ein still verschluckter Fehler.
**Testvorschlag:** Round-Trip-Test — exportieren, importieren, Anzahl und Felder vergleichen.

## 🟠 6. `interval_ms` in der API ist in Nanosekunden

**Fundstelle:** `cmd/cron/main.go:35` — `Interval time.Duration` mit Tag `json:"interval_ms"`.
`time.Duration` serialisiert als Nanosekunden. Die Persistenzschicht rechnet korrekt um
(`taskToData`: `int64(t.Interval / time.Millisecond)`), die API nicht.

**Beleg** für einen 30-Minuten-Task:

```
API  (GET /cron/tasks)   interval_ms = 1800000000000
Datei (tasks.json)       interval_ms = 1800000
```

Faktor 10⁶ Unterschied bei gleichem Feldnamen.

**Wirkung:** Jeder externe Konsument der API rechnet falsch. Aktuell fällt es nicht auf, weil
das eigene Frontend das Feld nicht anzeigt — ein fremder Client hätte keine Chance.

**Vorschlag:** Eigener Antworttyp mit `interval_min` (die Einheit, in der die API auch
entgegennimmt), oder mindestens ehrlich in Millisekunden umrechnen. Nicht den Feldnamen an
die Nanosekunden anpassen — die Eingabeseite arbeitet in Minuten, die API sollte eine Einheit
haben, nicht drei.

## 🟠 8. Gelöschte Tasks stehen nach einem Neustart wieder auf

**Fundstelle:** `cmd/cron/main.go:737` — der Wiederholungsversuch wird über
`time.AfterFunc(retryDelay, func(){ runTaskOnce(t) })` geplant. Der Rückruf hält einen
Zeiger auf den Task, prüft aber nicht, ob es ihn noch gibt, und `runTaskOnce` endet mit
`persistTask(t)`.

**Beleg:** Task mit `retry_count: 1`, `retry_delay_sec: 4`, Kommando `exit 1` anlegen,
ausführen, sofort löschen:

```
DELETE /cron/tasks/{id}          -> 204
sofort danach in tasks.json      -> 0 Treffer   (korrekt gelöscht)
6 Sekunden später in tasks.json  -> 1 Treffer   (der Retry hat ihn zurückgeschrieben)
GET /cron/tasks                  -> 0 Treffer   (in-memory ist er weg)
nach Neustart des Dienstes       -> Task ist wieder da, Status "running"
```

**Wirkung:** Zwei Schäden. Erstens läuft das Kommando eines gelöschten Tasks **noch einmal**,
als root. Zweitens ist der Task nach dem nächsten Neustart wieder aktiv — ein Zombie, den der
Nutzer nachweislich entfernt hatte. Dasselbe gilt für Pausieren: der hängende Retry ignoriert
den Status.

**Vorschlag:** Den Retry an denselben Abbruchmechanismus hängen wie den Zeitplan — Timer im
Task merken, in `clearSchedule` stoppen — und in `runTaskOnce` vor dem Ausführen prüfen, ob
`tasks[taskID]` noch existiert und auf `running` steht. Zusätzlich `persistTask` gegen
gelöschte IDs absichern (nicht speichern, was nicht mehr in der Map ist).

## 🟠 9. `priority` und `allow_parallel` tun nichts

**Fundstellen:** Beide Felder existieren in `Task` (`cmd/cron/main.go:55`, `:59`), in
`createReq` (`:314`, `:316`), in `TaskData` (`internal/storage/storage.go:30`, `:32`), werden
in `taskToData`/`dataToTask` hin- und herkopiert — und **nirgends gelesen**. Es gibt keinen
Vergleich, keine Sortierung, keine Verzweigung darauf.

**Beleg:** Grep über `cmd/` und `internal/` nach beiden Bezeichnern: ausschließlich
Deklarationen und Kopierstellen, keine Auswertung.

**Beworben werden sie trotzdem:**
- `README.md`: „**Priority System** – Set task priority (1-10)" und „**Parallel Execution
  Control**"
- `FEATURES.md` Abschnitt 4 und 5 führen beide als Feature mit Beispielwerten

**Vorschlag:** Entscheiden und dann ehrlich sein — entweder implementieren
(`priority` als Reihenfolge beim Abarbeiten der Warteschlange; `allow_parallel = false` als
Sperre gegen überlappende Läufe desselben Tasks, was bei langen Kommandos und kurzen
Intervallen heute tatsächlich passieren kann), oder aus UI, README und FEATURES.md entfernen.
Ein Schalter, der nichts tut, ist schlechter als kein Schalter: der Nutzer verlässt sich darauf.

## 🟡 10. Kein Bearbeiten von Tasks

Die Routenliste (`cmd/cron/main.go:207–220`) kennt `GET`, `POST`, `DELETE` und die Aktionen
`run`, `toggle`, `logs` — **kein** `PUT`/`PATCH`. Jede Änderung an einem Kommando, einem
Zeitplan oder einer Benachrichtigung erzwingt Löschen und Neuanlegen, samt Verlust der
gesamten Ausführungshistorie. Für einen Scheduler ist das die auffälligste Lücke im
Funktionsumfang.

## Anhang: die beiden Wegwerf-Proben

Beide lagen während der Messung als Testdateien in `cmd/cron/` und wurden danach wieder
entfernt — als aktive Tests im Repo wären sie sofort rot und würden die CI brechen, bevor
über die Fixes entschieden ist. Sie sind hier abgelegt, damit die Belege ohne Neuentwicklung
wiederholbar sind. Für den späteren Fix taugen sie als Vorlage; dann gehören sie als echte
Tests ins Repo (siehe Befund 11).

**A — Tagesfelder (Belege für Befund 1 und 2).** Als `cmd/cron/probe_cronnext_test.go`
ablegen, `go test ./cmd/cron/ -run TestProbeCronNext -v`:

```go
package main

import (
	"testing"
	"time"
)

func TestProbeCronNext(t *testing.T) {
	from := time.Date(2026, 8, 26, 0, 0, 0, 0, time.Local) // ein Mittwoch
	for _, c := range []string{
		"0 2 * * 1",       // nur Montag 02:00
		"30 3 * * mon",    // Alias Montag
		"0 2 * * mon-fri", // Bereich mit Aliasen
		"0 0 1 jan *",     // 1. Januar
		"0 5 1 * *",       // 1. des Monats
		"*/15 * * * *",    // Positivkontrolle
	} {
		n := cronNext(c, from)
		if n.IsZero() {
			t.Logf("%-18s -> NIE (Nullzeit)  | Validator: %v", c, isValidCron(c))
			continue
		}
		t.Logf("%-18s -> %s (%s) | Validator: %v",
			c, n.Format("2006-01-02 15:04"), n.Weekday(), isValidCron(c))
	}
}
```

Gemessenes Ergebnis am 2026-08-28: `0 2 * * 1` → Mittwoch 02:00, `0 5 1 * *` → Mittwoch
05:00, `0 0 1 jan *` → Nullzeit bei `Validator: true`.

**B — Race und Panic (Beleg für Befund 3).** Als `cmd/cron/probe_race_test.go` ablegen,
`go test -race ./cmd/cron/ -run TestProbeSchedulerRace`:

```go
package main

import (
	"testing"
	"time"
)

func TestProbeSchedulerRace(t *testing.T) {
	task := &Task{ID: "probe1", Name: "probe", Command: "true", Type: "interval",
```

## 3. Phasen

### Phase 0 — Hygiene und Basis (½ Tag)

1. Branch `release/0.2.1` von `main`.
2. **Binaries aus git:** `git rm --cached raw/usr/bin/cron`; `.gitignore` ergänzen um `/zima-cron`, `/cron`, `*.raw`, `raw/usr/bin/cron` (`.git` ist 32 MB durch das getrackte 6-MB-Binary; CI baut frisch).
3. **Host-Adresse aus `test_deployment.sh:10`** durch Parameter/Platzhalter ersetzen (BLOCK-Fund). Hinweis: bleibt in der Git-Historie; das ist zu benennen, nicht zu verschweigen.
4. **Eine Versionsquelle:** `version` in `main.go` bleibt; `build.sh` und CI schreiben `?v=<version>` in `index.html` (heute `0.2.1` vs. `0.2.0`).
5. **PR #1 mergen** (Unit-Namen), zusätzlich in die Unit:
   - `RequiresMountsFor=/DATA/AppData` (KB §42: `/DATA` ist ein spätes Bind-Mount, `local-fs.target` ordnet nicht dahinter; die 30×2-s-Warteschleife im Code bleibt als Gürtel)
   - `StandardOutput=journal` / `StandardError=journal`
   - **kein** `TZ=` (siehe Messung), **kein** `PrivateTmp` (Template „Cleanup Temp Files" räumt `/tmp` des Hosts)
6. **PR #2 reviewen und mergen** — vor eigenen Änderungen an denselben Stellen, sonst Konflikte und verbrannte Community-Arbeit. Review-Punkte: `mergeNotificationCredentials` (maskierte Werte dürfen nicht als echte gespeichert werden), Webhook-Format-Switch (jedes Format ein Fixture), `PUT` hält `mu` während `applyCreateReq` (Deadlock-Prüfung mit `startSchedule`, das `clearSchedule` ruft), `app.js` ist minifiziert — Diff nur mit `js-beautify` lesbar.
7. **CI:** `go vet`, `go test -race`, Matrix `amd64`/`arm64` (`build.sh` kann es schon), `sha256sum` als Release-Asset, `extension-release.cron` je Arch mit `ARCHITECTURE=x86-64` bzw. `arm64` (vorher auf dem Zielhost prüfen, dass `systemd-sysext refresh` das Feld akzeptiert — `systemd-sysext status`).

### Phase 1 — Scheduler-Korrektheit (Befund 1, 2, 3, 11) (1 Tag)

1. `cronNext` + `parseCronField` aus `cmd/cron/main.go` nach `internal/cron` verschieben (`Next(expr, from)`), damit sie testbar sind — heute hat `cmd/cron` **keine** Testdatei, und der Kern des Produkts ist ungetestet.
2. **Tests zuerst, rot sehen:** Probe A aus dem Audit als Tabellentest mit festem `from` und erwartetem Zeitstempel je Ausdruck (nicht `> 0`), plus Äquivalenztest D2.
3. Fix `dayOk` als `switch` (PR #2 bringt ihn; falls PR #2 zuerst gemergt ist, nur den `*/n`-Fall ergänzen): `*/n` im Tages-/Wochentagsfeld setzt **nicht** `isAll`.
4. Aliase zentral: `weekdayAlias`/`monthAlias` aus `validate.go` sind die einzige Namensauflösung; `parseCronField` nutzt sie für Einzelwerte **und** beide Seiten eines Bereichs (`mon-fri`, `jan-mar`).
5. **Race (Befund 3):** Ticker-Kanal einmal vor der Goroutine binden, `done` als einziges Abbruchsignal; `scheduleCronNext`-Rückruf liest `t.Status` und schreibt `t.NextRunAt`/`t.timer` unter `mu`. Probe B als Test unter `-race`.
6. **Neuer Fund N1:** `next_run_at` in `tasks.json` ist immer der **alte** Wert — `runTaskOnce` persistiert, *danach* setzt `scheduleCronNext` den neuen Wert ohne Persist (gemessen: Datei sagt `2026-09-18 04:00`, Uhrzeit war 10:04). Nach `scheduleCronNext` persistieren.
7. `test_deployment.sh`: den Cron-Fall auf einen **wochentagsgebundenen** Ausdruck umstellen und den erwarteten Wochentag vergleichen — `0 3 * * *` ist die einzige Klasse, die Befund 1 nicht trifft.

### Phase 2 — Datenintegrität (Befund 5, 6, 7, 8, 9, 12) (1 Tag)

1. **Export/Import** (5): gemeinsamer Austauschtyp mit `interval_min`; Antwort `{"imported":n,"skipped":[{"name","reason"}]}`; UI zeigt Übersprungenes. Round-Trip-Test D4.
2. **API-Einheit** (6): Antwort liefert `interval_min` (und `interval_ms` als **echte** Millisekunden, nicht Nanosekunden). Frontend liest `interval_min`.
3. **Logs löschen persistieren** (7): `persistTask(t)` nach `t.logs = nil`.
4. **Zombie-Retry** (8): Retry-Timer im Task merken, `clearSchedule` stoppt ihn; `runTaskOnce` prüft vor dem Lauf `tasks[id]` existiert und `Status == running`; `persistTask` speichert keine ID, die nicht mehr in der Map ist.
5. **Attrappen** (9) — Empfehlung: `allow_parallel=false` **implementieren** als Überlappungssperre (läuft der Task noch, wird der neue Tick übersprungen und als `skipped: still running` geloggt — bei langen Backups und kurzen Intervallen passiert die Überlappung heute wirklich). `priority` als **Sortierschlüssel der Liste** im UI (ehrlich, billig) — oder streichen. → **Entscheidung Maintainer.**
6. Import validiert wie Anlegen (eine Funktion `validateCreateReq` für beide Pfade, auch für `PUT`).
7. Abhängigkeiten: Zyklus beim Anlegen/Bearbeiten ablehnen (DFS über `depends_on`); Altersgrenze für „Erfolg zählt" optional (Default: kein Limit, Feld `dep_max_age_min`).
8. **Neuer Fund N2 — Template „Docker Cleanup":** `docker system prune -af --volumes` löscht **alle** nicht benutzten Volumes — bei einer gestoppten App deren Daten. `--volumes` aus dem Template entfernen, Beschreibung anpassen. (Wirkung: *Annahme* aus der Docker-Semantik, auf dem Zielhost nicht provoziert.)
9. **Neuer Fund N3 — Persistenzgröße:** `tasks.json` ist 266 KB für **3** Tasks (100 Logs × bis 4000 Zeichen), und jeder Lauf schreibt die ganze Datei neu. Bei 500 Tasks wären das zweistellige MB je Lauf. Logs in `logs/<id>.json` je Task auslagern; `tasks.json` hält nur Definitionen. Migration beim ersten Start (alte Datei mit `logs` lesen, aufteilen, Original als `tasks.json.pre-0.3` behalten).

### Phase 3 — Auth und Absicherung (Befund 4) (1–2 Tage)

**Vorlage:** `~/dev/zfw/internal/auth/auth.go` (398 Zeilen, ES256, JWKS-Cache mit TTL/Max-Stale, Issuer-Menge `casaos`/`zimaos`, 10 Tests) und `cmd/zfwd/main.go` (`resolveJWKSURL`, `sameOrigin`, `buildHandler`). Nicht neu schreiben — kopieren, Paketpfad anpassen, Tests mitnehmen.

1. `internal/auth` übernehmen. JWKS-URL über die Gateway-Routentabelle auflösen (`/.well-known/jwks.json → 127.0.0.1:37815` gemessen, Port ist vom System vergeben — **kein** Default hartkodieren, Loopback-Pflicht wie ZFW-S1). `CasaOS-Common` liefert keine Lookup-Funktion → wie ZFW `/var/run/casaos/routes.json` lesen (root-lesbar; der Dienst läuft als root) oder `GET {management.url}/v1/gateway/routes`.
2. Middleware vor alle `/cron/*` außer `/cron/health`.
3. **CORS:** Spiegelung entfernen. Same-Origin-Prüfung für `POST/PUT/DELETE` (ZFW `sameOrigin`): `Origin`/`Referer` muss zum `Host` passen, sonst 403. Test mit fremder Origin (D6).
4. **Frontend:** ein `api()`-Wrapper wie in ZFW (`Authorization: Bearer localStorage.access_token`); bei 401 sichtbare Meldung „Sitzung abgelaufen — ZimaOS-Oberfläche neu laden" statt stummem Leerbild.
5. **Fehlerantworten als JSON** `{"error":"…","code":"name_required"}` — Voraussetzung für Phase 4 (Übersetzung im Frontend über `code`).
6. **Unit-Härtung, bewusst schmal:** Tasks sind beliebige Root-Kommandos (Docker, `/DATA`, `/tmp`), daher **nicht** `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`. Sinnvoll: `ProtectKernelTunables`, `ProtectKernelLogs`, `ProtectControlGroups`, `RestrictRealtime`, `LockPersonality`. Jede Option gegen die sieben Templates testen (jedes einmal ausführen, Exit 0).
7. `test_deployment.sh` bekommt einen Token-Parameter (Login über `POST /v1/users/login`, Token aus `data.token.access_token` — KB §41.4) und die Fälle D6.

### Phase 4 — Frontend: Mehrsprachigkeit + ZFW-Design (2 Tage)

**Ausgangslage:** `app.js` ist ein 24-KB-Einzeiler (41 Zeilen), i18n als `{zh:{…},en:{…}}` inline, Sprache fest `lang='en'` beim Start, Umschalten nur per Dropdown, Backend-Texte (`Execution completed`, `Skipped: dependency not met`, Template-Namen) englisch hartkodiert. Frontend liegt **doppelt** (Wurzel + `raw/…`), `build.sh` kopiert drei von vier Dateien.

1. **Eine Quelle:** `raw/usr/share/casaos/www/modules/cron/` wird die einzige; Wurzelkopien löschen; `build.sh`/CI kopieren nichts mehr. (Das Gateway liefert die Dateien direkt aus `/usr/share/casaos/www/modules/cron/`, nicht aus dem Binary — `go:embed` hilft hier nicht.)
2. **`app.js` entminifizieren** und in lesbare Abschnitte gliedern (api, i18n, render, forms). Keine Build-Kette, kein Framework — bleibt Vanilla wie ZFW.
3. **i18n-Struktur:** `i18n/en.json`, `fr.json`, `de.json`, `zh.json` (oder ein `i18n.js` mit vier Objekten); jede sichtbare Zeichenkette über `t(key)`, inkl. Buttons, Platzhalter, Statusworte, Fehlermeldungen (`code` aus Phase 3), Template-Namen/-Beschreibungen (über Template-ID), Zeitformat über `Intl.DateTimeFormat(locale)`.

### Phase 5 — systemd/sysext und Upgrade-Pfad (½ Tag + Reboot-Test)

**Heutige Integration (gelesen aus `raw/usr/lib/systemd/system/cron.service`, `installWatchdog()` in `main.go`, gemessen auf dem Zielhost):**

```
sysext cron.raw ─┬─ /usr/lib/systemd/system/cron.service   (Restart=always, RestartSec=5, StartLimitIntervalSec=0, als root)
                 ├─ /usr/bin/cron                            (schreibt beim Start die 4 Units unten nach /etc, wenn Inhalt abweicht)
                 └─ /usr/share/casaos/{modules/cron.json, www/modules/cron/*}
/etc/systemd/system/ (persistent, überlebt sysext refresh + Reboot)
                 ├─ cron-watchdog.timer   OnBootSec=15 → cron-watchdog.service: is-active || start   (deckt den multi-user.target-Race, KB §18.9)
                 └─ cron-refresh.path     PathChanged=/usr/bin/cron → cron-refresh.service: sleep 2 && restart   (deckt Modul-Update ohne Reboot)
Gateway: Route /cron → 127.0.0.1:<zufälliger Port>, asynchron registriert, 60 Versuche × 2 s
```

Zustand auf dem Zielhost: alle vier Units vorhanden (01.04.), Timer `elapsed`, Path `waiting`, `cron.service active` — die Konstruktion **funktioniert**. Zu korrigieren:

1. Unit-Namen (PR #1), `RequiresMountsFor`, Journal-Ausgabe, Härtung (Phase 3.6).
2. `installWatchdog()`: Beschreibung des Timers stimmt nicht („after sysext refresh" — ein Refresh bootet nicht; der Timer deckt den **Boot**-Race). `FEATURES.md` sagt „45 seconds", die Unit sagt `OnBootSec=15` — Doku angleichen. **Timer behalten** (der Audit-Vorschlag „streichen" widerspricht KB §18.9, wo der Boot-Race mit echtem Reboot belegt ist).
3. `extension-release.cron` je Architektur (Phase 0.7).
4. **Upgrade-Pfad** — muss über das installierte v0.2.0 gehen, exakt so wie `zpkg` es tut:
   - Sicherung: `cp /DATA/AppData/cron/tasks.json …/tasks.json.pre-0.3` (macht der Dienst beim ersten Start selbst, Phase 2.9)
   - `zpkg remove cron` → stoppt Dienst? entfernt `/var/lib/extensions/cron.raw`? **Messen** (`systemctl is-active cron`, `ls /var/lib/extensions/` danach), nicht annehmen. Die `/etc`-Units bleiben — der neue Start überschreibt sie bei Inhaltsänderung.
   - `zpkg install cron.raw` → `cron-refresh.path` sieht die neue Binary → Neustart nach 2 s. Zeuge: `journalctl -u cron-refresh.service`, dann `health.version`.
   - D10, D11 mit **echtem Reboot** des Zielhosts (nach Absprache — dort laufen weitere Dienste).
5. **dcron** bleibt unangetastet (read-only `/usr`, OS-Bestandteil, tut nichts, niemand hängt daran). Ein `systemctl mask dcron` wäre ein Eingriff ins OS ohne Nutzen. → **Entscheidung Maintainer**, Empfehlung: nicht anfassen; im README einen Satz, dass ZimaOS' Stock-`crond` keine konfigurierbare Fläche hat und dieses Modul der Scheduler ist.
